# UI Spec Skill

引导开发者完成页面 UI 规划，产出标准化的 UI 描述文档，供后续代码生成阶段使用。

## 产出目标

- **产出物**：`ui-spec-<page-name>.md`——一份文档既是**输入**（用户填写布局/视图/数据实体）也是**输出**（Agent 派生组件清单/文件树/Store 代码）。
- **不是产出物**：UI 代码本身。本 skill 不写 `.vue` / 业务逻辑，只产描述文档。
- **下游消费者**：脚手架工具或后续代码生成阶段，依据此文档生成页面骨架。
- **单文件模型**：不再区分 spec 与 plan，用户填写部分与 Agent 派生部分共存于同一文档，工作流中按需累进补全。

> 文档的命名与存放规则见「输出文件格式」节。

**描述形式选择原则**（贯穿整个文档）：

| 内容性质 | 形式 | 典型场景 |
|---------|------|---------|
| **层级/分组结构** | YAML | 布局嵌套关系、组件按区域分组 |
| **平铺属性集合** | 表格 | 字段定义、API、按钮、实体结构、自定义组件 |
| **视觉结构** | ASCII 示意图 | 布局、视图结构 |
| **代码** | 代码块 | Store 实现、文件树 |

> 判定标准：能否用"父子包含"或"分组"关系组织？能则 YAML；只是同构条目罗列则表格。表格对用户更友好，YAML 对层级更明确——两者配合，不二选一。

## 技术栈前提

- 产出目标项目为 **Vue 3 + Pinia + MUSSEL UI v4** 的业务消费方项目（非 MUSSEL 组件库本身）。
- 开始前确认目标项目的 `mussel` 版本是否为 `4.0.*`，若不符，提示用户确认。
- 组件名一律采用 MUSSEL 4 真实组件（`mu-*` kebab 形式描述用途，正式清单用 `MuXxx` 组件名）。**不要凭记忆杜撰组件**——任何组件选型都需对照 `mussel-ui` skill 的 `references/components/*.md`，源码与文档冲突时以源码为准。

## 工作流程

输入引导是流程的**起点环节**，而非独立前置机制。整个流程按 6 个阶段推进，**但路径不止一条**：

```
Phase 0 → 判定模式
           ├─ 模板模式：直接输出空白文档 → 结束
           ├─ 精简逆向模式：输入是完整设计图 / 现有代码
           │     Agent 自动填满 1–7 节 → 一次性汇总确认 → 输出文档（不逐 Phase 停顿）
           └─ 规划模式：已有文档 / 草图 / 提问 → 归一化填入文档 1–4 节
                ↓
Phase 1 → 布局描述（确认 1 节，Agent 补示意图）
Phase 2 → 主要视图描述（确认 2 节，Agent 补示意图）
Phase 3 → 数据实体与 API 描述（确认 3 节）
Phase 4 → 组件选择确认（Agent 填 5 节）
Phase 5 → 文件树与 Store（Agent 填 6、7 节）
          ↓
      输出 ui-spec-<page-name>.md
```

**两条路径的差异**：

- **规划模式**（Phase 1–5）：逐段推进，每个 Phase 都遵循「先看归一化数据 → 补缺失 → 再确认」，等待用户确认再继续。
- **精简逆向模式**：输入足够完整时，Agent 一次性填满 1–7 节，最后做单次汇总确认，**不逐 Phase 停顿**。详见下方「精简逆向模式」节。

**规划模式下每个 Phase 1–5 都遵循同一输入处理逻辑**：

1. **先看归一化数据**：从 Phase 0 输出的结构化数据中，取本 Phase 对应字段作为初始输入。
2. **补缺失**：缺失/为空/模糊时，按本 Phase 的"提问清单"向用户收集。
3. **再确认**：把综合后的结果整理给用户确认，再进入下一 Phase。

> 即：输入决定"问什么、问多少"——输入越完整，提问越少；完全无输入时退化为纯提问驱动。

**规划模式下每个阶段结束后等待用户确认再继续。**

## Phase 0 — 输入引导

**目标**：收集用户的初始输入，归一化为结构化数据，为后续各 Phase 提供数据源。

**第一步：判定模式**——根据用户意图选择处理路径：

| 模式 | 判定依据 | 处理 |
|------|---------|------|
| **模板模式** | 用户直接要"空白模板/文档模板"（如"给我一个页面设计模板"、"生成 ui-spec 模板"），未提供具体业务信息 | 按下方路径规则输出一份空白 `references/ui-spec-template.md` 副本，**流程到此结束**，不进入 Phase 1–5 |
| **精简逆向模式** | 用户提供了**完整设计图**（设计稿/截图，能看出布局+视图+主要元素）或**现有代码**（页面源码路径/目录），要求"直接生成 spec"、"反向成 spec" | 进入下方「精简逆向模式」节，Agent 自动填满 1–7 节后一次性汇总确认 |
| **规划模式** | 用户提供了具体页面信息（业务描述/草图/已有文档/明确要规划某页面），但不足以支撑精简逆向 | 进入下方三类渠道收集，归一化后进入 Phase 1–5 逐段确认 |

> 模板模式下直接交付空白模板即可，不要追问页面细节——用户只是想要填空骨架。

> 三种模式优先级：模板模式最明确（关键词触发即结束）；其次精简逆向（要求完整输入：完整设计图或可用代码）；其余归规划模式。若用户给的图片只覆盖布局/视图、但缺业务语义，仍走规划模式逐段补全，而非精简逆向。

---

**规划模式**——用户输入有**三类渠道**，可单独或组合使用（如：图片给布局 + spec 给数据实体）。无论来源如何，最终都要**归一化为结构化形态**（YAML + 表格）进入各 Phase。

| 渠道 | 适用内容 | 形态 | Agent 处理 |
|------|---------|------|-----------|
| **① 已有 ui-spec 文档** | 全部 | 结构化（表格为主） | 直接解析对应节 |
| **② 图片**（设计草图/截图/参考页面） | 布局、视图结构 | 非结构化 | **视觉解析 → 转结构化 → 用户确认** |
| **③ 提问** | 缺失项 | 半结构化（对话） | 按提问清单收集 |

### 渠道 ① — 已有 ui-spec 文档

询问用户是否已有部分填好的 `ui-spec-<page-name>.md`。
- **有**：读取解析，把已填的 1–4 节作为各 Phase 初始输入；空缺节走渠道 ②/③ 补全。
- **无**：**按下方路径规则创建一份空白 `references/ui-spec-template.md` 的副本**，引导用户填写 1–4 节（用户可选用图片替代布局/视图节的填写，见渠道 ②）。

### 渠道 ② — 图片输入

用户可能提供设计草图、UI 截图、或现有页面截图来表达布局/视图结构（尤其布局和视图，比写 YAML 直观）。

**处理流程**：

1. **接收图片**：用户贴图或给路径，用视觉能力解析图中信息。
2. **识别与转译**：从图片提取结构化信息——
   - 布局：识别区域划分、位置关系、固定/可滚动、分隔等 → 转为 `layout` YAML
   - 视图：识别视图类型（表格/树/表单/Tab...）、列/字段/按钮等可见元素 → 转为对应表格
3. **明确标注不确定性**：图片能看出"长什么样"，但**看不出**：字段名（业务命名）、数据类型、API、交互逻辑、权限点。识别结果中，确定项与推测项要分开标注（如 `# [推测] 字段名：name`），避免把视觉推测当确定需求。
4. **转结构化后必须让用户确认**：把解析得到的 YAML/表格呈现给用户，逐项确认或修正，再进入下一 Phase。**不要跳过确认直接用**。

**按视图类型的识别指引**（图片能稳定看出的视觉线索 → 推断的结构化字段）：

| 视图类型 | 图片能识别 | 推断方法 | 标注 `[推测]` 的项 |
|---------|-----------|---------|------------------|
| 表格 `data-grid` | 列数、表头文字、操作列位置（行尾）、分页条、筛选区 | 数表头格 → 列数；表头文字 → 列标题；行尾按钮区 → 操作列 | 字段名（业务命名）、列类型（text/enum/date 难以肉眼区分）、可排序/可筛选 |
| 表单 `form-panel` | 字段数量、控件外观形态、必填星号、按钮 | 数字段；外观判控件（单行框=输入、下拉箭头=选择、滑块=开关、圆点=单选、方框=多选、日历图标=日期）；星号 → 必填 | 字段名、控件确切类型（select vs combo 难辨）、校验规则、字典选项 |
| 工具栏 | 按钮数量、主次（实色=primary）、图标按钮、筛选输入框 | 数按钮；主色填充 → primary；纯图标 → icon-button；下拉/输入框 → 筛选区 | action 名、权限点、图标语义 |
| 树 `tree-view` | 层级深度、展开/折叠、勾选框、节点操作 | 数缩进层级；方框 → 勾选；节点尾部图标 → 操作 | 节点字段名、懒加载、API |
| Tabs / Steps | 标签数量、激活态、步骤节点 | 数标签；下划线/填充 → 激活；数字+连线 → 步骤 | 各 tab/step 内容 |
| 卡片/列表 | 卡片数、列表项数、每项字段密度 | 数卡片/行；每项文字行数 → 信息密度 | 字段名、数据类型 |

> 控件外观相似的（如 `select` 不可输入 vs `combo` 可输入、`date` vs `time`），图片**无法可靠区分**，统一标 `[推测]` 让用户裁定，不擅自决定。

> 图片擅长表达"视觉结构"（布局怎么切、有哪些视图、表格大致几列），是 spec/提问的良好补充；但业务语义（字段叫什么、什么类型、哪个 API）仍需 spec 或提问补全。

### 渠道 ③ — 提问（补充）

无 spec、无图片，或两者覆盖不全时，按各 Phase 的提问清单逐项收集。这是兜底渠道，应尽量少用——优先引导用户用 spec 或图片一次性给齐。

### 归一化与汇报（规划模式）

无论用了哪几类渠道，规划模式下 Phase 0 结束前都要：

1. **归一化**：把所有输入合并、去重，统一为结构化形态（YAML + 表格），作为 Phase 1–3 的初始数据。
2. **汇报覆盖情况**：列出哪些 Phase 的信息已充分、哪些仍缺失需后续提问。让用户对"接下来还会被问什么"有预期。

## 精简逆向模式

判定为精简逆向模式后（见 Phase 0 模式判定表），**不走 Phase 1–5 逐段确认**，而是 Agent 自动填满文档 1–7 节，最后做一次性汇总确认。

**两类输入**：

| 输入类型 | 处理渠道 | 详细规则 |
|---------|---------|---------|
| **完整设计图**（设计稿/截图，能看出布局+视图+主要元素） | 渠道 ②（图片输入） | 见上方「渠道 ②」的识别指引，把识别结果**直接填入 1–5 节**（而非逐 Phase 确认）；6、7 节按 Phase 5 文件树规则与页面复杂度派生 |
| **现有代码**（页面源码路径/目录） | 渠道 ④（现有代码，见下方） | 按 `references/code-reverse.md` 的反向映射规则转写代码现状填入 1–7 节 |

**流程**：

1. **接收输入**：确认是图片还是代码路径/目录。
2. **自动填充 1–7 节**：
   - 图片：按渠道 ② 识别指引转译，识别结果直接填文档；推测项标 `[推测]`。
   - 代码：按 `references/code-reverse.md` 反向映射；遵循**忠实转写**原则——代码里有什么填什么，缺失的留空标 `-`，不臆造。
3. **一次性汇总确认**：整理一份「1–7 节填充情况」给用户——哪些节已填出、哪些是 `[推测]`/`-` 需用户补全或裁定。**单次确认，不逐 Phase 停顿。**
4. **用户补全后写入文档**：按「输出文件格式」与「产出前自检清单」写入。基本信息表「来源」填 `设计图` 或 `代码逆向`。

> 精简逆向与规划模式的根本区别：前者输入完整，省掉逐段确认的来回；后者输入不完整，靠逐 Phase 提问补齐。若逆向过程中发现关键信息大面积缺失（如代码无 store、图片只能看出布局），向用户说明，**必要时降级回规划模式**对缺失节逐段补全。

### 渠道 ④ — 现有代码

用户提供已实现页面的源码，要求反向成 spec。**详细反向映射规则见 `references/code-reverse.md`**，本节只列高层要点：

- **定位**：按 `src/pages/<page-name>/`（`index.js` + `views/` + `stores/`）约定定位；结构不符则按实际转写。
- **忠实转写**：只记录代码现状，不评判、不标注偏差、不给改进建议；缺失部分（如无 store/API）留空标 `-`，不臆造。
- **关键映射**：模板 `mu-*` 标签 → 布局/视图/组件清单；`<mu-table :columns>` 的 `columns` 数组 → 表格列；`<mu-form-field>` → 表单字段；`stores/*.js` 的请求 → API。映射细节与对照表查 `references/code-reverse.md`。
- **一次性确认**：填完 1–7 节后单次汇总确认（见上方精简逆向模式流程）。

### 文件命名与存放

ui-spec 文档与用户提供的图片共用同一套路径规则，详见「输出文件格式」节（唯一权威）。Phase 0 创建空白文档或读取已有文档时按该规则定位即可。

模板见 `references/ui-spec-template.md`。

### 文档各节 → 各 Phase 的映射

ui-spec 文档是用户填写（1–4 节）与 Agent 派生（5–7 节及示意图）共存的单一文件，各节对应关系：

| 文档节 | 填写方 | 对应 Phase |
|--------|--------|-----------|
| 基本信息 + 1. 布局 | 用户 | Phase 1（Agent 补布局示意图） |
| 2. 视图（含 2.1–2.6 各表） | 用户 | Phase 2（Agent 补视图示意图 2.7） |
| 3. 数据实体与 API | 用户 | Phase 3 |
| 4. 其他 | 用户 | 各 Phase 按需参考 |
| 5. 组件清单 | Agent | Phase 4 |
| 6. 文件树 | Agent | Phase 5 |
| 7. Store 职责 | Agent | Phase 5 |

> 单文件模型：用户填写部分与 Agent 派生部分在同一文档内，工作流中按节累进。图片输入在 Phase 0 转结构化后，等同于补全了文档的 1/2 节用户填写内容。

## Phase 1 — 布局描述

**目标**：明确页面的整体区域划分。

**输入来源**：ui-spec 文档的「1. 布局」节（用户填写的表格 + 布局类型）。若已填完整，直接进入确认；缺失时用以下提问补充。

向用户提问（可以合并成一次提问）：

1. 页面整体结构是什么？（如：顶部工具栏 + 左侧树 + 右侧内容区 / 全屏表格 / 主从布局 / 弹窗表单等）
2. 是否有固定区域（header/footer/sidebar）？内容区是否需要滚动？
3. 区域之间是否有分隔线、可调整宽度（SplitPane）等交互？

**输出格式**（写入 ui-spec 文档「1. 布局」节，含嵌套关系 + 区域属性表）：

布局类型：`split` | `full` | `master-detail` | `modal` | `custom`

区域嵌套关系（缩进表达父子包含，体现区域如何组合）：

```yaml
layout-tree:
  page:                  # 页面根
    - toolbar            # 顶部工具栏（横向通栏）
    - content:           # toolbar 下方的内容区
        direction: row   # row=横向 | column=纵向
        children:
          - sidebar
          - main
```

区域属性表：

| 区域名 | 位置 | 尺寸 | 固定 | 可调整 | 可滚动 | 说明 |
|--------|------|------|:----:|:------:|:------:|------|
| toolbar | top | 48px | ✓ | ✗ | ✗ | 工具栏 |
| sidebar | left | 240px | ✗ | ✓ | ✓ | 左侧树 |
| main | center | auto | ✗ | ✗ | ✓ | 主内容区 |

> 位置：`top` / `bottom` / `left` / `center` / `right`。表格描述各区域属性，但**无法表达嵌套**（如 toolbar 在 top，下方才是 left+center 的横向分割；或 main 内再套 tabs）；嵌套关系必须用上方的缩进结构补充。

**布局示意图**（Agent 派生，追加到「1. 布局」节末尾）：

```
┌───────────────────────────────────────────────────────────────┐
│                            MuToolbar                          │
├───────────────────────┬───────────────────────────────────────┤
│                       │               MuTable                 │
│        MuTree         │            ( data-grid )              │
│      ( tree-view )    ├───────────────────────────────────────┤
│                       │             MuPagination              │
└───────────────────────┴───────────────────────────────────────┘
        sidebar 240px                  main (auto)
```

**绘制规则**：

- 边框字符：`┌─┬─┐│├─┼─┤└─┴─┘`；区域内空位用空格填齐。
- 每个区域**中央**填写该区域的**视图名（来自 Phase 2）或主要组件名**；二者皆有时写 `组件名 ( 视图类型 )`，独占一行或两行。
- 固定高度区域（toolbar/header/footer）用单行表示；可滚动区域用多行留白示意。
- 尺寸、可调整性等元信息标在框外下方（如 `sidebar 240px`、`main (auto)`），不在框内混排。
- 弹窗/抽屉等浮层用独立小框单独绘制，不画进主布局。
- 示意图是辅助理解用的，**表格是结构化数据源**；二者需保持一致，改一处要同步另一处。

**⚠️ 示意图生成后必做的对齐检查**（产出文档前逐条核对）：

1. **垂直对齐**：所有 `│`、`┌┐└┘├┤┬┴┼` 必须位于同一列，每行宽度严格相等（含末尾的 `│`）。可用 `awk '{ print length, $0 }' file` 自检，所有行长度应一致。
2. **CJK 全宽陷阱**：区域中央若填中文/全角字符，**一个 CJK 字符占 2 列**。计算居中或对齐时按"显示宽度"而非字符数算。**为降低对齐难度，区域中央文字尽量只用 ASCII**（组件名/视图类型本就是英文）；中文描述放到框外注释。
3. **水平对齐**：`├` 与 `┤` 必须与上下行的 `│` 同列；多区域分隔线 `┬┴` 必须落在相邻区域的垂直边界上。
4. **闭合检查**：每个矩形框必须四角闭合（`┌┐└┘`），不能缺角；`├┬┤`、`├┴┤`、`┼` 必须有对应的 `│`/`─` 衔接。
5. **视觉验证**：在等宽字体下目视，所有横线 `─` 连续无错位、所有竖线 `│` 成一列无锯齿。
6. **内容覆盖**：示意图中的每个区域必须与「区域嵌套关系」+「区域属性表」的节点一一对应，不多不少；中央填写的组件名必须出现在 Phase 4 组件清单中。

> 若检查不通过，宁可简化示意图（减少行数/缩短文字）也要保证对齐——错位的示意图比没有更糟。

> 说明：`type` 是抽象布局意图，对应到 MUSSEL 4 的布局原子样式或布局组件在 Phase 4 完成（MUSSEL 4 提供的是布局原子组件 `MuHBox/MuVBox/MuSplitHBox/MuSplitVBox/MuGridBox`，没有应用级 `Layout` 容器）。

**列表类** — 以行/卡片为单位展示多条记录，核心场景是"浏览 + 批量操作"

| 视图类型 | 说明 |

**详情类** — 聚焦单条记录，展示或编辑完整信息

| 视图类型 | 说明 |
|---------|------|

| 视图类型 | 说明 |
|---------|------|

| `steps-view` | 步骤向导，线性流程，如多步表单 |
| `accordion` | 折叠分组，适合字段较多的详情页 |

**分析 / 统计类** — 以数据可视化为主，非 CRUD 操作

| 视图类型 | 说明 |
|---------|------|
| `dashboard` | 仪表盘，多图表 + 统计卡片组合 |

| `calendar-view` | 日历维度组织数据，适合排班、日程 |
| `gantt-view` | 甘特图，项目进度和时间区间展示 |

**空状态 / 过渡类** — 视图切换中的必要占位

| 视图类型 | 说明 |
|---------|------|
| `empty-state` | 无数据或未选中时的占位视图 |
| `loading-state` | 异步请求中的骨架屏或 spinner |
| `error-state` | 接口失败或权限不足时的提示 |

**视图结构示意图（按视图类型分级处理，非强制）**：

并非所有视图都适合 ASCII 描绘。按下表分级：

| 分级 | 视图类型 | 处理方式 |
|------|---------|---------|
| ✅ 强适合 | `data-grid` `tree-view` `form-panel` `detail-panel` `tabs-view` `steps-view` `accordion` | **必须**画结构示意图 |

**强适合视图的示意图参考**（每个视图一张，**内部文字只用 ASCII**，遵守 Phase 1 的对齐检查规则）：

```
data-grid                   tree-view                form-panel
┌────┬──────┬────────┐      ┌──────────────┐         ┌────────────────┐
│ id │ name │ action │      │ - root       │         │ name  [______] │
├────┼──────┼────────┤      │   + node-a   │         │ code  [______] │
│ 1  │ A    │ edit   │      │   - node-b   │         │ type  (select) │
│ 2  │ B    │ del    │      │     + leaf-1 │         │ desc  [______] │
│ .. │ ..   │ ..     │      │     + leaf-2 │         │         [save] │
└────┴──────┴────────┘      └──────────────┘         └────────────────┘

detail-panel                tabs-view                 steps-view
┌──────────────────┐       ┌────────────────┐        ┌──────────────────┐
│ name  : A        │       │ [tab-a] tab-b  │        │  1 --- 2 --- 3   │
│ code  : 001      │       ├────────────────┤        │  basic-contact-ok│
│ type  : ...      │       │                │        ├──────────────────┤
│ ...              │       │   ( panel )    │        │   step content   │
└──────────────────┘       └────────────────┘        └──────────────────┘

accordion
┌──────────────────┐
│ v  group-a       │      (v = expanded)
│    name  [____]  │      (^ = collapsed)
│    code  [____]  │
│ ^  group-b       │
│ ^  group-c       │
└──────────────────┘
```

绘制要点：
- `data-grid`：表头一行 + 数据行（用 `├─┼─┤` 分隔），列名用字段名，操作列标动作。
- `tree-view`：用 `-` 表节点、`+`/无前缀表叶子，缩进对齐表示层级（展开/折叠用文字标注，不用全角箭头）。
- `form-panel` / `detail-panel`：左侧字段名、右侧控件/值（`[____]` 表输入、`(select)` 表下拉、`[save]` 表按钮）。
- `tabs-view`：`[tab-a] tab-b` 表示激活/非激活，下方 `( panel )` 表内容区。
- `steps-view`：顶部 `1 --- 2 --- 3` 线性流程，下方内容区。
- `accordion`：`v`/`^` 标注展开/折叠的分组（避免用 `▼▶` 全角符号破坏对齐）。

## Phase 5 — 文件树确认

**目标**：规划页面的文件目录结构，与用户确认后输出最终 Plan。

**输入来源**：不直接来自文档填写节，而是基于基本信息中的 `page-name` + Phase 1–3 推导的页面复杂度，规划文件结构（是否拆分 stores、视图数量等）。

文件树规则（适用于业务消费方项目，基于团队约定）：

```
src/pages/<page-name>/                 # 页面私有代码
  index.js               # 页面入口，负责布局组合
  views/                 # 页面视图（Vue 组件）
    main-view.vue        # 主视图，文件名固定
    <view-name>.vue      # 其他视图，kebab-case
  stores/                # Pinia Store
    store.js             # 不拆分时固定文件名
    <store-name>.js      # 需拆分时按业务域命名（kebab-case）

src/common/components/<component-name>/  # 跨页面公共代码（仅在被多页面复用时放此）
  <view-name>.vue        # 组件视图，kebab-case
  <store-name>.js        # 组件 store（可选），API 同样内联其中
```

**关键约定**：

- **页面私有代码** → `src/pages/<page-name>/`：
  - **入口文件**：`index.js`（非 `index.vue`），负责布局组合与子视图编排。
  - **视图目录**：`views/`，每个视图一个 `.vue` 文件。
  - **主视图固定名**：`main-view.vue`，无论业务模块叫什么。其他视图按用途 kebab-case 命名（如 `dept-tree.vue`、`edit-form.vue`）。
  - **Store 目录**：`stores/`（复数）。单一 store：固定 `store.js`；需拆分：`<store-name>.js`（如 `list-store.js`、`tree-store.js`）。
- **跨页面公共代码** → `src/common/components/<component-name>/`：
  - **判定标准**：只有当某段视图/store 逻辑被 **≥2 个页面复用** 时才放此；页面私有的逻辑不要提前下沉。
  - **目录结构**：与页面一致——视图 `.vue` 直接置于组件目录下，store `.js` 同级。
  - **命名**：组件目录名、视图文件名、store 文件名均 kebab-case（公共组件没有"主视图固定名"概念）。
- **API 内联**：无论页面还是公共组件，**接口请求都直接写在对应的 store 文件中**（作为 store 的 action 或导出的请求函数），不单设 `api/` 目录。
- **依赖方向**：`src/pages` 可引用 `src/common/components`；`src/common/components` 不得反向引用具体 `src/pages`，否则复用性破坏。

向用户确认文件树后，文档全部章节已补全（5–7 节由 Agent 填入）。

3. **示意图对齐**：布局图与各视图示意图按 Phase 1「对齐检查」6 条通过（行宽一致、竖线同列、矩形闭合、ASCII-only 内部文字）；可用 `awk '{ print length }' file` 自检行宽。
4. **示意图 ↔ 结构一致**：布局图的嵌套层次与 1 节「区域嵌套关系」一致、区域与「区域属性表」行行对应；视图图字段与 2.x 表格列对应；组件名出现在 5 节清单。
5. **组件真实性**：5 节每个组件名都在 `mussel-ui/references/components/*.md` 中存在；控件类型按 Phase 4 对照表映射，无杜撰。
6. **自定义组件闭环**：5 节自定义组件表每行都有"原因 + 降级方案"（首版可不实现但需标注）。
7. **API 闭环**：3.2 API 表的端点覆盖视图操作（create/edit/delete/test 等都能在 API 表找到对应行）；Store 代码（7 节）调用的 API 都在 3.2 表中。
8. **表达规范**：中文描述 + 英文技术标识符；用户填写节用表格为主，Agent 派生节含 ASCII 示意图与代码块。
9. **代码逆向一致性**（仅代码逆向模式）：spec 各节须与代码现状一致——代码有的如实登记，代码缺失的对应字段标 `-`，不臆造；`[推测]` 项单独标注。

## 修订与迭代

文档创建后，用户可能回头改需求（加字段、改布局、加按钮等）。处理原则：

1. **识别已有内容**：读取现有 ui-spec 文档，识别哪些节已填写、哪些是 Agent 派生。
2. **定位影响范围**：用户改动只影响特定节时，按依赖关系推导波及的下游节——
   - 改 1 节（布局）→ 重画 1 节示意图；可能影响 5 节布局组件、6 节 index.js。
   - 改 2 节（视图/字段/按钮）→ 重画对应视图示意图；影响 5 节组件、7 节 Store actions。
   - 改 3 节（实体/API）→ 影响 7 节 Store API 调用。
3. **只重做受影响节**：保留用户填写的其他节原样，不重写整个文档。
4. **标注修订**：在文档顶部基本信息区记录修订日期与摘要（可选）。

> 不要因为局部修改而重写整个文档——会丢失用户精心填写的细节。

## 错误处理（fallback）

执行中遇到异常时的处理：

| 场景 | 处理 |
|------|------|
| `mussel-ui/references/components/*.md` 不存在或过时 | 不凭记忆杜撰组件；改查 MUSSEL 4 源码 `src/components/`（组件 `name` 字段为 `MusselXxx`）；仍无法确认时向用户说明并标记"待核对" |
| 用户给的图片无法解析或质量太差 | 不强行推测；向用户说明图片不清晰，请其改用文字描述或重新提供 |
| spec 文档字段与模板结构不符 | 按模板结构归一化（如用户用 YAML 写布局则转为表格）；保留用户原始信息，不丢失语义 |
| 用户描述的需求超出 MUSSEL 4 能力（如需复杂图表/富文本） | 在 5 节登记为自定义组件，注明原因与降级方案；不在文档中假装 MUSSEL 4 支持 |
| Phase 间信息矛盾（如表格列字段与实体字段不符） | 以用户最新确认为准，向用户指出矛盾点请其裁决 |
| 代码逆向时识别不到任何 `mu-*` 组件 | 向用户说明可能非 MUSSEL 页面，请确认后再处理；不强行转写。其余代码逆向异常（目录不符约定、状态散落视图内、`columns` 动态生成等）见 `references/code-reverse.md` 错误处理表 |
