# 结构重构（复杂功能模块，行为不变）

## 目标与判据

重构目标**不是**代码美观，是**提升 agent 对代码的功能检索与影响面分析效率**。所有排序、取舍、验收都用同一条判据：

> agent 能否只靠静态手段（import 图、文件头、函数签名、grep）回答两个问题——"这功能在哪？""改这里影响谁？"

由此推出适用边界：

- 适用：行为不变的依赖梳理、文件/目录拆分、重命名、转口消除、重复代码合并、参数形态收敛。
- 不适用：新功能开发、要改行为的语义重写、性能优化、纯格式化。原因：本流程的验证体系（等价性证明、行为基线）建立在"行为不变"假设上，行为要变时基线方法失效。

文中沿用一门语言栈的措辞（import 图、build、grep、git diff）；换栈时替换为等价工具（模块引用关系、编译或静态检查、全仓检索、版本差异），规则本身与语言无关。

## 根因模型：import 图 ≠ 依赖图

复杂模块"不好查"通常归结为一个根因：静态 import 关系不能代表真实依赖。四类失真源（识别操作见 references/signals.md 的 S1/S2/S3/S5）：

1. **re-export 聚合转口**：索引/聚合文件转发实现文件的导出，消费方指向聚合壳，实现被二跳遮蔽。
2. **运行时注入依赖**：模块间经参数袋（把回调和状态打包传入的大对象）互相调用，真实调用边只在运行时出现，import 图不可见。
3. **隐式共享可变状态**：大字段量状态对象被多文件共享引用，读写面无法从签名推断。
4. **跨层反向依赖**：低层 import 高层，影响面横跳，低层被高层传递闭包牵制。

## 总原则

1. **数据先行**：先建结构底图（分层模型 + 依赖图 + 关键链路 + 状态对象字段表），以数据定位问题，不凭感觉。
2. **按检索效率影响排序**，不按代码美学：先修根因级（依赖图失真），再修目录语义、重复代码、参数风格。
3. **机制优先于搬移**：先改"依赖可见性"（消转口、声明消费面、命名消歧），再动代码位置；搬移只用于切断重依赖边或建立单一事实源。
4. **小批交付**：每批独立可提交、独立可验证；批次容量按单会话负荷收敛，宁可多批不硬塞。
5. **"不做"清单与优化清单同权重**：逐条写明不做理由，防止范围膨胀。
6. **行为安全网前置**：先采基线后改码（硬顺序，见"探针基线硬规则"）。

## 六步流程

### 第 1 步：结构测绘

产出结构底图：分层模型、目录/模块依赖图、关键运行链路、横切关注点清单、参数形态与模块级状态盘点。

- 方法：按域提取函数级调用关系/签名/参数形态/模块级状态；精读枢纽文件（import 入度/出度异常者）。行数用 `wc -l` 排序，import 入/出度用引用源统计得出。多域可并行测绘（子代理按域分工）；单实例则逐域顺序完成。
- 痛点文件入围标准（三个独立代理指标联合定位，不单用行数）：行数排序头部 + import 入度/出度异常 + 文件头注释自述多职责。

### 第 2 步：问题清单

逐信号扫描（信号全集见 references/signals.md），产出编号清单 P1…Pn：按"检索效率影响"排序，每条附代码证据（`文件:行号`）。

### 第 3 步：优化设计

产出优化项清单：每项编号并对应一个问题项，标注批次、风险、验证方式。同时写"不做"清单（程序见 references/signals.md）。手段选择与次序规则见 references/means.md。

### 第 4 步：设计修订

先核对设计的三类高发失实：

- 消费方清单失实（漏列/误列）；
- 行号漂移（设计基于的快照与当前工作区不一致）；
- 批次容量与阻塞误判。

执行强度按可用条件分级：

1. 有独立评审者（另一 agent、异构模型或全新上下文）→ 交其独立审改上述三类失实，再由原设计者按核实结果定稿。
2. 无独立实例 → 自己按同一清单逐项核，但必须用命令核实，禁凭记忆与旧快照。

铁律（不因分级放宽）：设计中的文件清单与消费方**逐文件 grep 核实当前工作区**，不信转述、不信旧快照。

### 第 5 步：实施

- 改码前先采探针基线并落盘（硬顺序，见下）。
- 目标区存在未提交的在途改动时：先记录改动快照（status/diff），再做**行级避让**——只动 import/命名行，禁触逻辑区；无法避让则推迟该区域。
- 每批独立可提交、独立可验证。交付前本地跑 build/静态检查，通过再交验证方。

### 第 6 步：验证

优先由独立实例（非实施者本人/同上下文）执行；做不到时至少新开上下文，逐项执行并留存命令与输出——独立性是为了让验证不受实施者解释影响，留档可部分补偿。按改动类型选验证充分组合（见 references/verification.md），按低成本排除法次序：build → 残留扫描 → diff 等价 / API 冻结 → 探针基线 + 像素/渲染快照断言。前序通过不替代后序，只让后序聚焦。

## 信号速查与问题归类（浓缩）

| # | 信号 | 一句话识别 | 问题类 |
|---|---|---|---|
| S1 | re-export 转口 | 聚合文件转发的符号，import 源是另一实现文件，本文件无定义/包装 | A |
| S2 | 运行时注入依赖 | 参数袋的键被 ≥2 文件读/写，文件间无 import 边 | A |
| S3 | 隐式共享可变状态 | 单对象 >20 字段、写入点分布多文件，或依赖"使用前手动 sync"协议 | A |
| S4 | 同源重复 | 注释自认"copy of/逐字同源"，或 ≥2 文件函数体归一化后逐 token 相等 | C |
| S5 | 跨层反向依赖 | 分层模型中存在下层→上层 import 边，或单边拖入重载荷传递闭包 | A |
| S6 | 命名无区分度 | 高频短标识符全库 grep 命中巨大，且跨模块同形异义 | B |
| S7 | 文件/目录多职责 | 文件头自述多职责、行数排序头部、同文件导出互不消费的符号组 | B |
| S8 | 参数形态超标 | 位置参数 >5，或打包对象 >10 字段 | D |

问题类由信号直接映射：A 依赖图失真（S1/S2/S3/S5，"改这里影响谁"答不出）、B 检索信噪比（S6/S7，"这功能在哪"答不出）、C 同源漂移（S4，一处修复另一处漏、无机制提醒）、D 调用点可读性（S8，调用语义不可见）。

识别操作细节（grep 形态、双证据规则）、判定阈值、停止条件、不做程序 → 第 2 步前读 `references/signals.md`。

## 手段决策（浓缩）

| 问题类 | 信号 | 手段 | 强度/成本 | 关键前置 |
|---|---|---|---|---|
| A | S1 | 删转口，消费方直引实现文件 | 高 / 低-中 | 已核实属纯转发 |
| A | S2/S3 | 文件头 `@reads/@writes/@calls` 注解声明 | 中 / 低 | 保留参数袋，不重造注入机制；键名与注解前缀稳定 |
| A | S5 | 跨层共享纯函数独立成模块 | 高 / 中 | 函数为纯函数，无层内状态耦合 |
| B | S6 | 同名标识符消歧，高频标识符全库单义 | 中-高 / 低-中 | 新名不与既有符号冲突 |
| B | S7 | 目录语义拆分，文件名即检索词 | 高 / 高 | A 类已修（依赖图可信） |
| C | S4 | 逐字重复合并为单一事实源 | 高 / 中 | 有等价性校验点可逐条核对 |
| D | S8 | 参数收敛：>5 转打包，>10 按语义域分组 | 中 / 视调用点数 | 接触时渐进执行，不开专项批次（除非已引发实际缺陷） |

次序规则（先机制后搬移）：

1. **机制类（消转口/声明/改名）先于搬移类（拆模块/提取/目录拆分）**。原因：机制类只动 import/注释/命名行，diff 可逐行配对，走 M 类低成本验证通道；搬移类动文件边界，必须先采探针基线。混批则整批按所含最高要求类型验证。
2. **A 类先修，修完复测再进 B/C/D**。原因：依赖图失真状态下判定的拆分边界本身不可信。复测方法：用"目标与判据"的两问检验静态手段是否已能回答；未达标再继续。
3. **搬移只用于切断重依赖边（S5）或建立单一事实源（S4），不为美学搬移**；参数收敛只在接触调用点时顺带执行。

机理、成本与前置条件全集 → 第 3 步前读 `references/means.md`。

## 改动分类与验证组合（浓缩）

改动分类按 **diff 形态**判别（判别细则、补充手段与失效机理见 `references/verification.md`；下表为浓缩）：

| 类型 | diff 形态 | 充分组合（够用） |
|---|---|---|
| M 机械归一 | 仅 import 行改写、标识符替换、整块平移，无新逻辑 | build + 残留引用扫描 + diff 等价审计 |
| S 结构拆分 | 新文件 + 源文件删除块 + 两侧引用改写 | build + 残留扫描 + 探针基线（模块导出变化时加 API 冻结） |
| E 行为等价提取 | ≥2 处删除相似块 + 1 处新增定义 + 调用点改引 | build + 残留扫描 + 探针基线 + 等价性校验点核对 |
| C 签名收敛 | 签名与调用点参数列表同步变化 | build + 全调用点逐参数位核对 + 探针基线 |

## 探针基线硬规则

- **必须采基线**：S/E/C 类改动；M 类触及运行时动态查找（动态 import/键名拼接）；任何影响面不可静态推断的改动。
- **可豁免**（以 diff 等价审计替代）：纯 M 类，且不触及动态查找、不动行为路径。豁免合法性：须在设计文档写明理由与 diff 配对范围，经核对配对完整性后方可免采；**无记录的豁免视为未验证**。
- **顺序不可违反**：基线在改码前采集落盘。基线不可回溯——验证员无法事后补采，只能同口径复采后逐字比对。
- **职责归属**：基线采集是实施者职责，写进任务简报，不默认验证员兜底。

## 教训（硬规则）

1. 设计引用的消费方清单/行号会失实——实施前逐文件核实源码，不信转述。
2. 在途未提交改动会与重构混合作业——先做变动快照，设计标注行级避让，验证时区分归属，不误判越权。
3. 批次容量按执行槽位单会话负荷收敛——不同风险级不混批（机械归一与需设计+专项校验的改动分批），宁可多批不硬塞。
4. 基线不可回溯——采集职责写进任务简报，不能默认验证员事后补。
5. 漏网修复要"一次修净"——修单点前先全仓扫同类残余，避免多轮修复。
